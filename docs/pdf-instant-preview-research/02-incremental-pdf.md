# Incremental / page-level PDF generation: findings

Scope: can PolicyCraft's preview re-render only the affected page(s) instead of the whole document (currently 2–5 s per change via React SSR, Playwright `page.pdf()`, pdf-lib post-processing).
Labels: **[SRC]** = stated in a cited primary source. **[SRC-read]** = read from Chromium source via WebFetch (code path, not a benchmark). **[INF]** = my inference, not in any source. **[UNVERIFIED]** = secondary or search-snippet only.

## 1. Does `pageRanges` save time?

**Protocol and Playwright contract [SRC]**
- CDP `Page.printToPDF` has `pageRanges`: "Paper ranges to print, one based, e.g., '1-5, 8, 11-13'." Also `preferCSSPageSize`, and `transferMode` with enum `ReturnAsBase64` / `ReturnAsStream`. `transferMode`, `generateTaggedPDF`, `generateDocumentOutline` are marked experimental. Source: https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json (Page domain, roughly offset 1.1M–1.2M of the file).
- Playwright `page.pdf` `pageRanges` default is the empty string = all pages; `preferCSSPageSize` default `false` (content scaled to paper). Source: https://playwright.dev/docs/api/class-page
- Puppeteer PDFOptions: `printBackground` default `false`; `timeout` default `30000`; `waitForFonts` default `true`; `outline`/`tagged` experimental; no `transferMode` field exposed. Source: https://pptr.dev/api/puppeteer.pdfoptions

**Chromium code path [SRC-read]**
- `headless/lib/browser/protocol/page_handler.cc` (https://chromium.googlesource.com/chromium/src/+/main/headless/lib/browser/protocol/page_handler.cc): `PrintToPDF` takes `std::optional<String> page_ranges` and forwards `page_ranges.value_or("")` without parsing. `return_as_stream` is computed from `transfer_mode`; when true, `PDFCreated` calls `CreateIOStreamFromData` and returns a stream handle.
- `components/printing/renderer/print_render_frame_helper.cc` (https://chromium.googlesource.com/chromium/src/+/main/components/printing/renderer/print_render_frame_helper.cc): `CalculateNumberOfPages` runs `EnterPrintMode` on the **whole document** to get the total page count. Only indices in `pages_to_render_` are passed to `PrintPageInternal`, and layout for CSS page boxes (`ComputePageLayoutForCss`) runs inside that function. So excluded pages get no per-page layout or paint, but the full-document layout pass still happens.

**Conclusion [INF from the above]**
- `pageRanges` on the monolithic document saves per-page paint and PDF serialization for the skipped pages. It does **not** avoid the full-document layout, which is probably where most of the 2–5 s goes. Measure this first: time `pageRanges: "1"` vs. full print on the real document. If the times are close, the pageRanges route cannot reach an instant preview.
- The win comes from printing a **separate, smaller HTML document per section**, so layout only covers that section.

**Mode / engine notes**
- Chrome blog: old headless (now the `chrome-headless-shell` binary) "in some ways more performant" and has fewer dependencies; no PDF numbers given. https://developer.chrome.com/blog/chrome-headless-shell
- Playwright v1.49 notes: "New headless is slightly slower on average in our testing", and Playwright uses `chromium-headless-shell` when headless. https://github.com/microsoft/playwright/issues/33566
- A Chromium DevTools engineer (per a search snippet, bug not fetched) says PDF performance in new headless should match headful. **[UNVERIFIED]**
- Implication [INF]: `chrome-headless-shell` may be faster, but it can also change PDF output. Compare output with the same binary before switching.

## 2. Chunked printing and merging

**Forced page breaks make chunks independent [SRC]**
- CSS Fragmentation: `break-before: page` "Always force a page break before/after the principal box"; "A forced break overrides any break restrictions acting at that break point." https://www.w3.org/TR/css-break-3/
- Orphans/widows apply to unforced breaks only.

**Constraint that matters for "exactly as today" [INF]**
- If today's sections flow continuously (a section starts mid-page), splitting by section changes the output, and a change in section A can shift every page after it. Page-level incremental re-render only works if each chunk starts on a fresh page with a forced break, or if the design accepts re-laying-out everything after the change. This must be checked against the current CSS before any chunking.

**Page numbers [SRC + INF]**
- `counter(pages)` (total pages) is generated by the UA and "cannot be manipulated": https://www.w3.org/TR/css-page-3/
- Chrome 131+ supports margin boxes and `counter(pages)`: https://developer.chrome.com/blog/print-margins . Per chunk, `counter(pages)` would be the chunk's total, not the document's.
- [INF] Stamp page numbers and footers in pdf-lib after merging (the pipeline already does pdf-lib post-processing). This removes per-chunk counters. Risk: the stamped output must match Chrome's rendering of margin boxes; check with a pixel diff.

**TOC page references [SRC]**
- Chromium does not implement `target-counter()` as far as I could find. Paged.js documents it as its own feature: https://pagedjs.org/documentation/-cross-references . A Chromium proposal to add it exists but I could only find it in search snippets. **[UNVERIFIED]**
- Prior art for two-pass: Prince's cookbook (write index in pass 1, consume in pass 2) and a Puppeteer-based loop (render, measure heading pages, re-render until two passes agree or 5 passes). The Puppeteer article is secondary. **[UNVERIFIED]**
- [INF] Two-pass works only if the TOC has a fixed page count. If the TOC changes length, every section's page numbers shift, so reserve a fixed number of TOC pages or iterate to convergence.

**Merging with pdf-lib [SRC]**
- `PDFDocument.copyPages(srcDoc, indices)` copies pages between documents; add them with `addPage`/`insertPage`: https://pdf-lib.js.org/docs/api/classes/pdfdocument
- `copy()` "won't copy all information over" (acroforms, outlines); expect similar limits for copied pages.
- pdf-lib issue #95 (secondary, search snippet): a large PDF took about 1300 s to load because of arrays of nulls; fixed in #99 (about 13 s). https://github.com/Hopding/pdf-lib/issues/95 **[UNVERIFIED]**
- [INF] Each separately printed chunk embeds its own copies of fonts and images, so merged output may grow. Check file size and whether duplicated font objects appear.
- No primary benchmark for `copyPages` speed was found.

## 3. Caching per-section PDFs

- [INF] Cache key must include everything that changes layout: HTML/CSS for the section, page size and `format`, `preferCSSPageSize`, `printBackground`, font set, Chrome version, page parity (for mirrored margins), and the section's starting page index (only if any page number is printed inside Chrome).
- Keep `preferCSSPageSize` and `format` identical across chunks. Playwright's default is `false`, which scales content to the paper size. Mixing settings would scale chunks differently.
- No source found on pdf-lib `copyPages` cost per page; measure it.

## 4. Keeping a page loaded and patching the DOM

- CDP `Page.setDocumentContent`: "Sets given markup as the document's HTML." (same browser_protocol.json, Page domain). Replacing the whole document means reparsing and relayout of everything.
- [INF] Patching only the changed section's DOM (via `page.evaluate`) and then printing only that section is the cheapest path. It still requires the section to be printed as an isolated document for the layout savings in section 1, so the patch must target a section wrapper that is itself printable.
- Fonts: `waitForFonts` defaults to `true` (Puppeteer PDFOptions), so each print waits for fonts. Keep fonts loaded in the persistent page to avoid repeated waits. Turning it off is a correctness risk, not a documented speedup.
- `transferMode: ReturnAsStream` is what Playwright uses for `pdf()`: https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/chromium/crPdf.ts (reads the result with `readProtocolStream`). Benefit (avoiding a base64 payload for large PDFs) is [INF]; no benchmark found.
- Known slow factors: Puppeteer issue reports of large outputs (>100 MB, high-res images) are older and from search snippets **[UNVERIFIED]**. Likely levers, all [INF]: downscale images before printing, avoid network fetches inside print, and check `printBackground` cost only if the page has background images.

## 5. Realistic lower bound for `printToPDF`

- **No primary benchmark found** for ms per `printToPDF` call for 1 vs 10 pages. The Browserless benchmark has navigation timings only (goto ~128–192 ms on example.com for Browserless, ~250–400 ms for others), with no PDF or setContent numbers: https://www.browserless.io/blog/how-fast-is-your-hosted-browser-a-practical-benchmark-for-automation-workloads
- One DEV post (single run, not averaged, search snippet only): launch ~169 ms, newPage ~88 ms, goto ~1019 ms, pdf ~110 ms. https://dev.to/chuongtrh/improve-performance-generate-pdf-using-puppeteer-4lg7 **[UNVERIFIED]**
- [INF] For a warm page holding one small section, a `printToPDF` call plausibly lands in the low hundreds of ms, with a floor near 100 ms from IPC and PDF serialization. This is a hypothesis, not a measured number. The 10-page cost depends on layout, which is the part pageRanges does not remove.

## 6. Recommended experiments (cheap, decisive)

1. On the real document: time `page.pdf()` full vs `pageRanges: "1"`, warm page, median of 10 runs. Tells whether layout or paint dominates.
2. Time a single section printed as a standalone HTML document (same CSS, same `preferCSSPageSize`/`format`).
3. Pixel-diff a chunked-and-stamped PDF against the current full output to check the "exactly as today" requirement.
4. Check whether current sections start on fresh pages (forced breaks). If not, chunking changes the output.
5. Compare `chrome-headless-shell` vs new headless output and timing with the same HTML.
